# Backend — Distributed Job Scheduler

FastAPI + PostgreSQL API, worker process, and cron scheduler process.
For the overall project (including the frontend and docs), see the
repo root `README.md`.

## Prerequisites

- Docker and Docker Compose
- (Optional, for running things outside Docker) Python 3.12

## Running it

1. Copy the environment file:
   ```bash
   cp .env.example .env
   ```
   The defaults work as-is for local development.

2. Start Postgres and the API:
   ```bash
   docker compose up --build
   ```
   This will:
   - Start Postgres and wait until it's healthy
   - Run `alembic upgrade head` to create every table
   - Start the FastAPI server with hot reload

3. Check it's alive:
   ```bash
   curl http://localhost:8000/health
   # {"status":"ok","database":"ok"}
   ```
   Interactive API docs: http://localhost:8000/docs

4. Stop everything:
   ```bash
   docker compose down          # stop containers, keep DB data
   docker compose down -v       # stop and wipe the DB volume
   ```

## Running workers

The worker is a separate long-running process from the API. `docker
compose up` starts one worker container automatically. To run several
workers at once (to see atomic claiming actually prevent double
execution across processes):

```bash
docker compose up --scale worker=3
```

Or run one manually outside Docker:
```bash
cd backend
python -m app.workers.worker --name my-worker --concurrency 5
```

Each worker: sends a heartbeat every 5s, checks for crashed workers
(missed heartbeats) every 15s and requeues their jobs, and polls for
claimable jobs every 2s -- claiming atomically via
`SELECT ... FOR UPDATE SKIP LOCKED` so multiple workers never grab the
same job. Send `SIGTERM`/`SIGINT` (Ctrl-C, or `docker compose stop`) for
a graceful shutdown: it stops claiming new work, finishes whatever's
in-flight, then marks itself STOPPED.

**Job handlers** are registered in `app/workers/handlers.py`, keyed by
the job's `name` field. Included for testing/demo purposes: `echo`
(always succeeds), `sleep` (succeeds after `payload.seconds`),
`always_fail` (always fails, for exercising retries/DLQ), and `flaky`
(fails until `payload.fail_until` attempts, then succeeds). Add your own
by registering a new key in `HANDLERS`.

## Running the backend without Docker (optional)

```bash
cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
# Point DATABASE_URL at a Postgres instance you're running yourself,
# e.g. docker compose up db -d, then in .env set host to localhost.
alembic upgrade head
uvicorn app.main:app --reload
```

## Database migrations

Migrations live in `alembic/versions/`. The initial migration
(`557cd0eb7eea_initial_schema.py`) creates all 13 tables, their enums,
foreign keys, and indexes in one go.

To create a new migration after changing a model:
```bash
cd backend
alembic revision --autogenerate -m "describe your change"
alembic upgrade head
```

Always read an autogenerated migration before applying it — autogenerate
is good but not perfect (e.g. it won't always detect column renames
correctly).

## Running tests

Tests run against a real Postgres database (not SQLite) since the schema
uses Postgres-specific types and later phases depend on real row-locking
behavior. Each test runs in its own transaction that's rolled back
afterward, so tests are isolated and fast without recreating tables
every time.

```bash
# Start a Postgres instance (the docker-compose one works fine):
docker compose up db -d

# Create a dedicated test database (once):
docker exec -it job_scheduler_db psql -U scheduler_user -c "CREATE DATABASE job_scheduler_test;"

cd backend
pip install -r requirements.txt
TEST_DATABASE_URL="postgresql+psycopg2://scheduler_user:scheduler_pass@localhost:5432/job_scheduler_test" \
  pytest -v
```

29 tests currently cover: registration/login/validation, JWT protection
of routes, organization creation and multi-tenant isolation, project
CRUD with authorization (a user can't see/edit/delete another user's
project — verified explicitly), queue creation with default and custom
retry policies, pause/resume (including that a non-member can't pause
someone else's queue), stats, and filtering.

54 tests total as of Phase 3-5, adding: job creation/validation per job
type, job authorization, the retry-then-DLQ lifecycle end to end
(including that manual retry from the DLQ actually resets and re-claims
the job), and -- most importantly -- **real concurrency tests**
(`tests/test_claiming.py`) that open several genuinely separate,
simultaneously-committing DB connections (not the usual per-test
transactional session) to prove no job is ever claimed twice, that
per-queue concurrency limits hold under concurrent load, and that paused
/ not-yet-due jobs are correctly excluded. `tests/test_heartbeats.py`
covers heartbeat recording and the crash-recovery path: a worker with a
stale heartbeat gets marked UNHEALTHY and its in-flight jobs are
requeued and become claimable again.

## What's implemented in Phases 1-5

- Full database schema (13 tables), verified against real Postgres with
  zero drift between the Alembic migration and the SQLAlchemy models.
- JWT authentication, multi-tenant organizations, full project/queue
  CRUD with authorization.
- **Job submission**: immediate, delayed, and scheduled jobs (batch is
  supported via a shared `batch_id`; recurring/cron jobs are deferred to
  the scheduler phase, since they need a genuinely different mechanism
  -- see below).
- **Atomic job claiming** via `SELECT ... FOR UPDATE SKIP LOCKED`,
  respecting per-queue `concurrency_limit` and `is_paused`, verified
  under real multi-connection concurrency to never double-claim a job.
- **Retry system**: fixed / linear / exponential backoff, configurable
  per queue (and inherited by jobs created in that queue), with the
  delay formula matching the spec (`base_delay * 2**retry_count` for
  exponential).
- **Dead Letter Queue**: jobs that exhaust `max_retries` are moved to
  DLQ with the failure reason and full retry history captured as JSON;
  supports manual retry via the API, which resets the job's attempt
  count and re-queues it.
- **Worker heartbeats**: each worker sends a heartbeat every 5s,
  recorded both as a live status on the `workers` row and as an
  append-only history in `worker_heartbeats`.
- **Crash recovery**: a periodic reaper (run by every worker) detects
  workers with a stale heartbeat, marks them UNHEALTHY, and requeues
  any job they had CLAIMED/RUNNING -- without consuming one of the
  job's own retry attempts, since a missed heartbeat is an
  infrastructure failure, not the job's fault.
- **Graceful shutdown**: SIGTERM/SIGINT stops new claims and waits for
  in-flight jobs before exiting.
- 54 automated pytest tests, including genuine multi-connection
  concurrency tests, run against real Postgres.

## What's intentionally NOT in Phases 1-5

- **Scheduler for recurring/cron jobs.** The `ScheduledJob` table
  (cron templates) exists in the schema but nothing evaluates cron
  expressions or spawns `Job` rows from them yet -- that's a genuinely
  separate mechanism (a periodic "what's due" scan) from the
  request/response job-submission API built so far.
- **Metrics dashboard endpoint** (`GET /metrics/dashboard`) -- per-queue
  stats exist (`GET /queues/{id}/stats`), but the cross-queue system
  overview endpoint doesn't yet.
- **Frontend dashboard** (all 9 React pages).
- **Idempotency keys** for exactly-once semantics -- this system is
  honestly at-least-once delivery (a job could in principle run twice if
  a worker crashes between finishing work and persisting COMPLETED);
  handlers are expected to be idempotent where that matters. This
  trade-off is called out explicitly in the code and will be revisited
  in the design decisions document.
