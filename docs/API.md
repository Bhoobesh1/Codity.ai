# API Documentation

Interactive, always-current documentation is auto-generated by FastAPI
and served at `/docs` (Swagger UI) and `/redoc` when the API is running.
This file is a human-readable companion covering things the OpenAPI
schema doesn't: authentication flow, authorization rules, and error
format.

## Authentication

1. `POST /auth/register` — create an account. Returns the user (no token).
2. `POST /auth/login` — exchange email+password for a JWT.
3. Every other endpoint (except `/health` and `/`) requires
   `Authorization: Bearer <token>`.

Tokens expire after 60 minutes by default (`JWT_ACCESS_TOKEN_EXPIRE_MINUTES`
in `.env`). There's no refresh-token flow — log in again once expired.

## Authorization model

- A **user** belongs to zero or more **organizations**, each with a role
  (`owner`, `admin`, `member`). Creating an organization makes you its
  owner.
- **Projects** belong to an organization; any member of that org can
  create/view/edit/delete its projects (no finer-grained role
  enforcement in the current version — see the design decisions doc).
- **Queues**, **jobs**, and **scheduled jobs** are all reached through
  their parent project's authorization — a queue is visible to you iff
  its project's organization has you as a member.
- **Workers** are a system-wide resource (a worker isn't scoped to one
  org — it pulls jobs from any queue), so `/workers` only requires being
  logged in, not membership in a specific org.
- **Metrics** (`/metrics/dashboard`) are scoped to the queues you can
  access; job counts reflect only your own organizations' data. Worker
  health counts are global (see the "why" in `metrics_repository.py`).

**Important**: requesting a resource that doesn't exist and requesting
one that exists but you can't access both return `404`, not `403` for
the latter. This is deliberate — a `403` would confirm the resource
exists, letting an attacker enumerate valid IDs. The one exception is
*creating* a resource under an organization/project you don't belong
to, which returns `403` (there's nothing to leak; you already know the
parent ID you tried).

## Error format

Every error response (from application-level exceptions, not FastAPI's
own validation errors) has this shape:

```json
{
  "error": {
    "code": "not_found",
    "message": "Project not found."
  }
}
```

Codes in use: `not_found` (404), `conflict` (409), `forbidden` (403),
`unauthorized` (401), `bad_request` (400).

Pydantic validation errors (malformed request bodies) instead return
FastAPI's default `422` shape with a `detail` array — these happen
before application code runs, so they're not wrapped the same way.

## Pagination

List endpoints that support it accept `page` (default 1) and
`page_size` (default 20, max 100) query params and return:

```json
{
  "items": [...],
  "total": 42,
  "page": 1,
  "page_size": 20,
  "pages": 3
}
```

## Job payload / handler contract

`Job.payload` is arbitrary JSON, dispatched to a handler function keyed
by `Job.name` (see `backend/app/workers/handlers.py`). The scheduler
sets this up automatically for recurring jobs from the `ScheduledJob`
template's own `payload`. There's no schema validation on payload
contents — handlers are expected to validate/handle whatever shape they
receive, the same way you'd validate any external input.
